# Data access and payloads

How a request reads and writes data, and how much it sends back. The evidence here comes mostly from studies of performance bugs in real applications built on object-relational mappers, so most rules are `research`. Bounding result sets and paginating lists is STB-04.

### DAT-01 · Related data in a fixed number of queries
Strength: MUST · Evidence: research · Check: static, trace, load

The number of queries a request makes does not grow with the number of items it returns. Related records are loaded with a join or with one query per relation (`WHERE id = ANY(...)`, an ORM's eager loading), never one query per item (N+1).

*Why:* in a study of twelve Rails applications, N+1 was "still prevalent", behind 15 problematic page actions and 9 reported issues; one fix merged 51 queries and cut a page from 1.10 s to 0.34 s [S30]. A static detector found hundreds of "one-by-one processing" instances and similar anti-patterns in Java applications, and fixing those it found improved response time "by up to 98%" and on average 35% [S31].

### DAT-02 · Write in batches
Strength: SHOULD · Evidence: research · Check: static, trace

Many rows are inserted or updated in batches (a multi-row `INSERT`, a bulk API, one transaction), not one statement and one round trip per row.

*Why:* more than a third of the 109 performance bugs in one study came from efficient calls combined inefficiently, such as one transaction per item where one batched call would do [S32]. In a 2026 dataset of database code generated by language models, row-by-row writes appeared in 48.8% of correct implementations when the prompt set no performance goal [S34].

### DAT-03 · Index what queries filter, join and sort on
Strength: SHOULD · Evidence: research · Check: static, trace

Columns used in `WHERE`, `JOIN` and `ORDER BY` on tables that grow, and foreign keys, have an index, added with the query and not after the table is large. Whether an index is needed is judged by the plan at realistic data size: on a small or low-selectivity table a sequential scan can be the right plan.

*Why:* in the Rails study, "missing index is the most common performance problem reported" in the applications' bug trackers, yet "it only appears in three out of the 40 problematic actions" in the latest versions, which suggests teams add indexes once a query has become slow in production [S30]. Catching it before the data grows is cheaper.

### DAT-04 · Fetch only what the caller uses
Strength: SHOULD · Evidence: research · Check: static, trace

A query selects the columns and loads the relations the response or computation needs, not whole rows and every association. A response returns the fields its caller uses.

*Why:* "excessive data", retrieving data that is never used, is one of the two ORM anti-patterns Chen et al. detect, alongside one-by-one processing [S31]. In the 2026 dataset, fetching unneeded columns was the most frequent defect in generated code, in about half of correct implementations [S34]. The cost per instance is often small, so this is a SHOULD.

### DAT-05 · Eager loading is bounded too
Strength: SHOULD · Evidence: research · Check: static, trace, load

Loading relations ahead of time fixes N+1 only when the relations are bounded. Eager loading a relation that grows without limit moves the problem from query count to memory.

*Why:* in one Rails application, eager loading pulled in hundreds of thousands of rows, "making the page freeze"; the study notes that "loading them all at once will create huge memory pressure" [S30].

### DAT-06 · No query whose answer is already known
Strength: SHOULD · Evidence: research · Check: static, trace

A request does not repeat a query whose result it already has: a query inside a loop whose arguments do not change with the loop, or the same lookup made twice in one request.

*Why:* "More than 10% of the performance issues are caused by (mis)using ORM APIs that lead to unnecessary queries being issued", including loop-invariant queries and queries with known results [S30]. In general software, "More than a quarter of bugs are caused by calling functions that conduct unnecessary work given the calling context" [S32].

### DAT-07 · Judge data access at production scale
Strength: MUST · Evidence: research · Check: report

ERLANG judges every data-access check on seeded data at a realistic size, and at ten times that size, comparing the two. A route that is fast on a development database proves nothing about the defects in this file.

*Why:* "About two thirds of performance bugs need large-scale inputs to manifest" [S32]. "developers usually only test their code on a small scale", while the problems surface at larger scales [S31]. The Rails study found its non-scalable page actions by testing at increased data sizes [S30].

### DAT-08 · Compress text responses
Strength: SHOULD · Evidence: platform · Check: static, load

Text responses (JSON, HTML, CSS, JavaScript) are compressed when the client offers it, with `Vary: Accept-Encoding` set. Formats that are already compressed (images, audio, video) are not compressed again.

*Why:* compression can give a "size reduction of up to 70%" for some documents, and is recommended for everything except already-compressed formats [S33].

### DAT-09 · A page loads its data in a fixed number of calls
Strength: SHOULD · Evidence: practice · Check: static, trace, load

The calls a page view makes to its own service do not grow with the number of items it shows. A list page gets what it shows for every item in one call, or one call per kind of data (`GET /products/prices?ids=...`), never one call per item.

*Why:* Microsoft names "implementing a single logical operation as a series of HTTP requests" as a cause of the Chatty I/O antipattern, which "can result in too many network round trips", and its fix is to "reduce the number of I/O requests by packaging the data into larger, fewer requests" [S39]. It is DAT-01's N+1 one layer up, between the page and the service.
