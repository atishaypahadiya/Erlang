# Output format

Generated by `scripts/reference.mjs` from `lib/erlang.js` and the schemas named below.

## Standard output

One line per finding, from this template:

```text
${f.severity.padEnd(7)} ${f.check}  ${loc ? `${loc.file}:${loc.line ?? ''}` : ''}  ${f.message}
```

Then one summary line, which begins with this template, followed by the reason when there is one and the report's path:

```text
${r.status}: ${fails} failing (${n('error')} error, ${n('warning')} warning), ${n('info')} info
```

The report file is a report/1 document holding finding/1 findings, each with Erlang's own fields under `erlang`.

## `core/schema/report.schema.json`

report/1. One run of one specialist on one subject, and its findings. A gate reads status before findings: only a complete run's findings say what is and is not wrong; a partial run's findings are true but do not cover everything; a refused run judged nothing, and its empty list of findings never means clean. The core fields below are reserved; a specialist may keep its own run data beside them. No field holds secret material, or a hash of it (see finding.schema.json). Adding an optional field keeps the format at report/1; renaming or removing a field, or adding a required one, makes it report/2. See protocol/04-inspect.md.

| Field | Type | Required | Description |
| --- | --- | --- | --- |
| `schema` | "report/1" | yes | |
| `specialist` | string | yes | |
| `version` | string | yes | The specialist's version. |
| `status` | "complete", "partial", "refused" | yes | complete: every check ran. partial: some did not (a step timed out, the page never showed what it was waiting for); the reason names them. refused: nothing was judged (the subject could not be reached, the run stopped before judging, or a guard declined to run it); the reason says why. |
| `reason` | string | no | Why the run is partial or refused. Required unless complete. |
| `subject` | string | no | What was inspected: a page's URL, a repository, a service. |
| `started` | string | no | When the run started, ISO 8601 in UTC. |
| `findings` | array | yes | Each a finding/1. Empty when refused. |

## `core/schema/finding.schema.json`

finding/1. One finding, in the format every specialist in the set writes (ITTEN, KERCKHOFFS, ERLANG). The core is the same for all of them; each keeps its own fields in an object named after itself, which this schema does not look inside. No field of a finding, its fingerprint and every extension included, holds secret material: a credential, token, key, password or session, or a hash of one. Name a secret by what it is (issuer, kind, prefix, length), never by its value. Adding an optional field keeps the format at finding/1; renaming or removing a field, or adding a required one, makes it finding/2. A report of findings is report/1 (report.schema.json). See protocol/04-inspect.md.

| Field | Type | Required | Description |
| --- | --- | --- | --- |
| `schema` | "finding/1" | yes | |
| `specialist` | string | yes | The specialist that wrote the finding, in lower case: itten, kerckhoffs, erlang. |
| `check` | string | yes | The check, as the specialist names it. |
| `severity` | "error", "warning", "info" | yes | |
| `fingerprint` | string | yes | The same for the same finding in every run, and different for different findings: two runs are compared by fingerprint. By convention the check, then the parts of where that identify the finding, joined by \|, as in contrast\|#nav > a or n-plus-one\|api\|GET /orders\|src/routes/orders.js#listOrders. Built only from what stays the same between runs: never a measured value, a report id, a host or port, a record id, or the element's text. |
| `message` | string | yes | |
| `measured` | array | yes | The paths of fields whose values differ between any two runs of the same subject (frame counts, durations, latencies, settle windows, benchmark figures). Dotted from the finding's root; [] means each item of a list; "message" means the numbers in the message. Everything not listed is compared exactly. |
| `floor` | "security", "accessibility", "null" | yes | The floor the check holds, if any. Where two specialists conflict, security floors come first, then accessibility floors, then craft (null). |
| `detection` | array | yes | How the finding was detected; one finding can rest on several. render: measured in a browser on a rendered page. static: read from source, history or build output without running it. config: read from configuration. trace: read from telemetry of a run at low rate (spans, query logs, process metrics). live: observed by sending requests to a running deployment of the owner's own app. load: measured under generated load. Not part of the fingerprint: the same defect found statically and then confirmed live is one finding. Compared as a set; the order carries no meaning. |
| `rules` | array | no | Optional. The rules the finding comes from, as IDs from the specialist's own reference (LAY-03, AUZ-01, DAT-01). Citations of outside standards (WCAG, CWE, ASVS) stay in the specialist's extension. |
| `where` | object | yes | What the finding is on: any of elements of a rendered page, places in code, endpoints of a service and named resources, at least one of them non-empty. A finding that shows in one place and is fixed in another lists both. |
| `where.elements` | array | no | |
| `where.locations` | array | no | |
| `where.endpoints` | array | no | |
| `where.resources` | array | no | |

## `schema/finding-erlang.schema.json`

finding/1, ERLANG's extension. The erlang object of a finding/1 written by ERLANG. Fields are added as checks need them; see research/finding1-requirements.md. Every static finding carries a fix; a trace finding carries one when its statement or route is found in the source, and its counts in trace either way; a load finding carries its measurements in load.
