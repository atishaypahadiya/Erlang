# Config keys

Generated by `scripts/reference.mjs` from `schema/config.schema.json`.

The config is read from erlang.config.json at the root of <dir>. How ERLANG scans a subject, read from the scan root only (lib/scope.js). Every report names the config, what it excludes, the handlers it names and the tables it calls small. Keys not listed here are refused.

| Key | Type | Required | Description |
| --- | --- | --- | --- |
| `exclude` | array | no | Paths relative to the scan root that are not part of the app, such as test fixtures with planted defects or generated reports. A directory (trailing / optional) excludes everything under it; a file excludes that file. No globs, no .., nothing absolute. |
| `handlers` | array | no | Request handlers ERLANG cannot find in the source, or entry points that are not HTTP routes (a queue consumer, a job). Each names a function by its name in a file; its code, and what it calls, is in the request path for the checks that judge what a request costs (lib/handlers.js). An entry that names nothing is a note in the report. |
| `handlers[].file` | string | yes | Relative to the scan root, with / separators. |
| `handlers[].function` | string | yes | A function declared in the file, by name. |
| `handlers[].method` | string | no | The HTTP method, or the operation in capitals for other protocols. |
| `handlers[].route` | string | no | A route template, such as /orders/:id; for a queue, its name. |
| `smallTables` | array | no | Tables (or Prisma models) the owner states stay small, such as settings or country codes: reading all of their rows is not reported by unbounded-query. Every report names them. |
| `database` | object | no | The database the deployed processes share, as its owner states it. pool-sizing compares every pool's connections against maxConnections less the 3 PostgreSQL reserves for superusers; without it, a managed database's limit is unknown and the finding is info. |
| `database.maxConnections` | integer | yes | PostgreSQL's max_connections, as set on the server (SHOW max_connections). |
| `warmup` | object | no | A cheap route the trace harness requests once in each fresh process before it times first requests (cold-start, STB-10), such as a health check that reads once through the app's database driver. It takes up the start-up cost every first request pays (the framework's first dispatch, the driver's first query, the runtime's work after listen), so a route is judged on its own set-up only. Without it the harness requests a path that does not exist and expects a 404, which warms the framework but not the database driver; every report says which warm-up ran. |
| `warmup.method` | string: "GET", "HEAD" | no | GET (the default) or HEAD: the warm-up must not change anything. |
| `warmup.path` | string | yes | A path on the app itself, starting with a single /; no host. |
