# Failure model

What web services written by coding agents are most likely to get wrong under load, in rank order, and how each defect can be found: in the source, in traces from a short run, or by a local load test. ERLANG's checks and fixtures follow this list.

## What the evidence can and cannot support

No study has measured web applications written by coding agents under load. The ranking below rests on four kinds of evidence, of different strength:

1. **Bug studies of human-written database-backed applications.** The strongest is Yang et al. (ICSE 2018): 204 performance issues in twelve open-source Rails applications, 140 from their bug trackers and 64 found by the authors' profiling [F1]. Chen et al. (ICSE 2014) found hundreds of ORM anti-pattern instances in one Java application with a static detector [F2]. Jin et al. (PLDI 2012) studied 109 performance bugs in general software [F3].
2. **One controlled study of database code generated by language models.** A replication artifact on Zenodo, for a paper accepted at Informatics 2026 (the paper's text was not available; the artifact's data was read): 900 single-shot generations, from three models, in three ORMs, over five data-access tasks, each run against PostgreSQL at two data sizes [F4]. It tests one function at a time, with no tools and no feedback, so it says nothing about defects that span files, which is where agents' N+1 queries usually arise.
3. **Incident studies.** Retry policies sustained more than half of 22 metastable outages from 11 organisations [F5]. Missing timeouts are among the root causes of timeout bugs in cloud systems, most of which produce no error message [F6].
4. **Studies of agents' pull requests.** These describe process, not defects: agents' performance pull requests include explicit performance validation less often than humans' (45.7% against 63.6%) [F7], and performance tasks are among those agents fail most often to get merged [F8].

So the top three ranks rest on measured frequency and impact. Ranks 4 to 6 rest on the LLM study and on mechanism. Ranks 7 to 12 are judgment: the impact mechanisms are well documented (the reference rules), but no study gives their frequency in web-application code, human or generated. The ranking orders defects by expected harm (how often, times how bad when it happens), then breaks ties by how cheaply ERLANG can catch the defect before merge.

The LLM study also points at the remedy ERLANG relies on. Adding a performance goal to the prompt, without naming a technique, cut column over-fetching from 73% to 25% of correct implementations and session memory bloat from 60% to 12% [F4]. The defects come from defaults, not from inability, which suggests (but has not shown) that feeding findings back to the agent will fix most of them.

Rank 12 is not in the brief's list of defects. It is here because it decides whether the service passes CAP-02, ERLANG's main load oracle, and because a service with every other defect fixed can still collapse past its knee without it.

Connection-pool exhaustion (8) is often the symptom through which 1, 3, 6, 7 and 9 become visible under concurrency. ERLANG reports the root cause where it can tell, and pool exhaustion only when no root cause is found.

## The defects

Each entry gives what goes wrong, the evidence, and how each channel can detect it. **Static** works on source and migrations. **Trace** works on OpenTelemetry spans, database statement logs and process metrics from a short scripted run at low rate. **Load** is a local load run against the owner's own service. Counts are preferred to timings wherever a defect has a count, since a count is the same on every machine.

### 1 · Per-item queries (N+1 reads, row-by-row writes)

A list is loaded with one query, then each item's related data with one more query per item; or a batch is written one row per statement. Cost grows with the data, and small development databases hide it.

*Evidence.* In Yang et al., the inefficient data-access category, which includes N+1, holds 44 of the 204 issues; N+1 itself is "still prevalent", in 15 problematic page actions and 9 reported issues. One fix merged 51 queries and cut a page from 1.10 s to 0.34 s. Most fixes needed "fewer than 5 lines of code change" [F1]. Chen et al.'s detector found 228 one-by-one processing instances in one Java application, and fixing the anti-patterns it found improved response time "by up to 98%" and on average 35% [F2]. In the generated-code study, N+1 reads were rare (3 of 126 correct implementations), but row-by-row writes, measured as statement amplification against a hand-written reference, appeared in 48.8% of implementations when the prompt set no performance goal [F4].

*Static.* A query or ORM lazy-load inside a loop over a result set; an insert or save inside a loop. Framework guards exist: Rails' `strict_loading` raises on lazy loading [F12]; the Bullet gem reports missing eager loading [F13]; Django's `assertNumQueries` asserts a query count in tests [F14].

*Trace.* Many database spans with the same statement shape under one request span. OpenTelemetry database spans carry the query text, parameterised by default, which makes the grouping possible [F10]. Sentry's detector looks for "sequential, non-overlapping database spans with similar descriptions", above a total duration and a span count [F15]. `pg_stat_statements` groups statements that differ only in their constants and counts their calls [F11].

*Load.* No concurrency needed: run the route with the list ten times longer (a larger page, or ten times the seeded data for a route that is not paginated) and compare statements per request. A bounded route makes the same number; an N+1 route makes about ten times as many. The generated-code study uses this ratio test at two data sizes [F4]. It is deterministic, so it runs on a laptop with no load generation at all.

### 2 · Unbounded queries and missing pagination

A list route returns every matching row, or takes its page size from the client without a cap.

*Evidence.* Yang et al.: "the most common cause for scalability problems" is a page that displays every record satisfying a condition, behind 15 of 34 page actions that did not scale; in bug trackers it was "always fixed by pagination" [F1]. Jin et al.: about two thirds of performance bugs need large inputs to show [F3]. The generated-code study's pagination numbers are not usable: the task asked for paging, and its detector found few of the cases human reviewers flagged [F4].

*Static.* A list query with no `LIMIT` or paginator; a page size read from the request without a maximum.

*Trace.* Rows returned per statement (`pg_stat_statements` rows divided by calls [F11]; the opt-in `db.response.returned_rows` span attribute [F10]); response bytes.

*Load.* Response size and latency at 1× and 10× seeded data. A bounded route stays flat.

### 3 · Missing indexes

A query filters, joins or sorts on a column with no index, which is fast on development data and slow at production size.

*Evidence.* In Yang et al., "missing index is the most common performance problem reported" in the applications' bug trackers (30 of 140), yet "it only appears in three out of the 40 problematic actions" in the latest versions: teams add indexes after deployment, once a query becomes slow [F1]. ERLANG's value here is catching them before the data grows.

*Static.* Columns used in `WHERE`, `JOIN` and `ORDER BY`, from SQL and ORM calls, compared with the indexes declared in migrations. Foreign keys without an index.

*Trace.* `EXPLAIN` on the statements captured during the run, against seeded data at realistic size, looking for sequential scans of large tables. PostgreSQL's `auto_explain` logs slow statements' plans automatically, but its timing option can have "an extremely negative impact on performance" [F16], so ERLANG runs `EXPLAIN` itself after the run.

*Load.* Latency of the route against the clean twin. Weaker than the plan, which says why.

### 4 · Over-fetching, oversized payloads and chatty APIs

Whole rows or objects fetched and returned when the caller uses a few fields; responses not compressed; a page that needs many small calls where one would do.

*Evidence.* The most frequent defect in the generated-code study: column over-fetching in 64 of 126 correct implementations, at the same rate in all three ORMs, falling from 73% to 25% when the prompt asked for performance [F4]. In human code it is a smaller category (9 of 204 issues for unnecessary data retrieval) [F1], and many of Chen et al.'s excessive-data fixes made no significant difference [F2], hence its rank below 1 to 3 despite its frequency.

*Static.* `SELECT *` or whole-entity loads on list routes; no compression middleware.

*Trace.* Response bytes per request; client calls per page view; `Content-Encoding` on responses to a request that offers `gzip` and `br` [F17].

*Load.* Bytes per request and time to load one page view, against the twin.

### 5 · Memory growth

Memory that rises with data or with uptime: a whole result set loaded to iterate over, a module-level cache keyed by request data with no bound, an ORM session that keeps every inserted object.

*Evidence.* In the generated-code study, memory bloat in the ORM session appeared in 60% of decidable cases without a performance goal and 12% with one [F4]. In Yang et al., one eager load pulled in 276,220 rows, "making the page freeze" [F1]. Unbounded in-process caches and true leaks are not measured in any study found.

*Static.* `findAll()` or `.all()` without a limit, followed by iteration in memory; a module-level map or array that is only ever added to; bulk writes in one session without flushing.

*Trace.* Resident memory and heap against requests served: a sawtooth is healthy, a ramp is not.

*Load.* A soak run at moderate rate with varied keys, and the same route at 1× and 10× data, comparing peak resident memory. This class needs time: a short run will not show a slow ramp.

### 6 · Retry storms

Retries with no cap, no backoff or no jitter, retries at several layers of one call chain, or retries of overload replies. Harmless in tests and in brief failures; under overload they multiply the load that caused the failure.

*Evidence.* In a study of 22 metastable failures from 11 organisations, "the most common sustaining effect is due to the retry policy", in more than half of them [F5]. The arithmetic is in the reference rules: 243× and 64× amplification from per-layer retries [S18][S19]. How often application code gets this wrong is not measured.

*Static.* Retry loops and retry libraries, checked for a maximum attempt count, a growing delay, randomness in the delay, and which status codes they retry. Nested retries across layers, when both layers are in the repository.

*Trace.* Client spans to the same dependency under one parent, and the gaps between them: equal gaps mean no jitter, zero gaps no backoff.

*Load.* With the upstream stub returning errors, the attempts it receives per user request (a count), and whether the service recovers once the stub recovers.

### 7 · No timeouts on outbound calls

An HTTP, database or cache call that can wait forever, because no timeout was set and the client library's default is long or unlimited.

*Evidence.* A study of timeout bugs in eleven cloud server systems lists missing timeouts among the root causes, and finds that 60% of timeout bugs produce no error message [F6]. Nygard: socket reads often "block forever" by default [S23]. Frequency in web-application code is not measured.

*Static.* The cheapest check in the set. Bandit's B113 already finds Python `requests` and `httpx` calls with no timeout [F9]; ERLANG needs the same for `fetch`, axios, database drivers and pools in each language it supports. A static check cannot see a timeout set in configuration elsewhere, so it reports what it could not resolve as unknown, not as a defect.

*Trace.* Spans to a dependency whose durations have no ceiling.

*Load.* With the upstream stub accepting connections and never replying (TMO-08): in-flight requests and open sockets should level off at the timeout, not grow for the length of the run.

### 8 · Connection-pool exhaustion

Every pooled connection is in use, so requests queue for one and time out. Causes: a pool smaller than the concurrency it serves; a connection held across a slow call to another service; a connection not released on an error path; a new pool created per request; a pool larger than the database can serve.

*Evidence.* No frequency study. HikariCP's pool-sizing page gives `connections = ((core_count * 2) + effective_spindle_count)`, from the PostgreSQL project, "as a starting point", and reports a demonstration in which shrinking a pool cut response times from about 100 ms to about 2 ms [F18]. The mechanism is Little's law: connections held equal arrival rate times hold time, so a slow dependency multiplies them (CAP-08).

*Static.* A pool or client constructed inside a handler; an acquire with no release in `finally`; an `await` on another service while a connection is held; pool size against expected concurrency.

*Trace.* Time waiting for a connection; connections checked out; PostgreSQL connection count against its maximum.

*Load.* Errors acquiring a connection as concurrency passes the pool size; for leaks, checked-out connections that never return to idle over a soak run.

### 9 · Heavy synchronous work in the request path

CPU-bound or blocking work done inline: password hashing, image processing, large JSON, synchronous file or process calls, sending email. On an event-loop runtime one such request stalls every other request.

*Evidence.* Node's documentation: while the event loop is busy with one client, "all current and new clients will not get a turn"; it lists `crypto.pbkdf2Sync`, synchronous `zlib` and `fs` calls, and very large `JSON.parse` among the things to keep out of servers, since "the Event Loop should orchestrate client requests, not fulfill them itself" [F19]. Frequency is not measured.

*Static.* A list of synchronous and CPU-heavy calls (starting from Node's) found inside request handlers; email or image libraries called in handlers.

*Trace.* Event-loop delay; long spans with no I/O beneath them.

*Load.* The latency of a route that does no work (a health check), measured while the heavy route is under load. On a correct service it does not move.

### 10 · No caching and redundant computation

The same expensive work repeated: a loop-invariant query inside a loop, the same aggregate recomputed for every request although its inputs change rarely.

*Evidence.* In Yang et al., unnecessary computation and inefficient computation each account for more than 10% of issues [F1]; Jin et al. found that more than a quarter of bugs are work that could have been skipped [F3]. Whether a cache should exist is often a design choice, not a defect, which keeps this class low.

*Static.* A query inside a loop whose arguments do not depend on the loop.

*Trace.* The same statement with the same parameters, repeated within one request or across consecutive identical requests. Parameter values are opt-in in OpenTelemetry [F10], so ERLANG turns them on for its own runs.

*Load.* Throughput of the route against the twin.

### 11 · Cold starts

A slow first request after a deploy or restart: lazy initialisation inside a handler, an empty cache that carries capacity, connections opened on first use.

*Evidence.* AWS: cold starts "typically occur in under 1% of invocations" and last from under 100 ms to over 1 s; "The largest contributor of latency before function execution comes from initialization code" [F20]. A platform property more than a code defect, hence its rank. The SRE book treats the empty capacity cache as a cascading-failure risk (CAP-11) [S18].

*Static.* Heavy work at first use inside a handler, rather than at startup.

*Trace.* A long initialisation span on the first request only.

*Load.* First-request latency after a restart against steady state, and goodput when load arrives at once on a cold instance (CAP-03).

### 12 · No load shedding

The service accepts every request and queues it, with no limit on concurrency or queue length. Under overload every request is late instead of some refused, and goodput falls.

*Evidence.* The reference rules: fail early and cheaply [S18], bound requests in flight [S18][S21], and keep goodput flat past saturation [S17][S18][S21]. No frequency data.

*Static.* No concurrency limit or queue bound in front of handlers. Weak, since limits are often set in a proxy or platform outside the repository.

*Load.* The CAP-02 test: offered load stepped past the knee. The clean twin keeps goodput flat and refuses the excess quickly; the planted service's goodput falls and its p99 grows without bound.

## Detection summary

| Defect | Static | Trace | Load | Needs seeded data | Needs fault injection | Needs time |
|---|---|---|---|---|---|---|
| 1 Per-item queries | strong | strong | count ratio | yes | no | no |
| 2 Unbounded queries | strong | strong | count ratio | yes | no | no |
| 3 Missing indexes | medium | strong (plans) | weak | yes | no | no |
| 4 Over-fetching, payloads | medium | strong | medium | yes | no | no |
| 5 Memory growth | medium | medium | strong | yes | no | yes |
| 6 Retry storms | strong | medium | strong (count) | no | yes | no |
| 7 No timeouts | strong | weak | strong | no | yes | no |
| 8 Pool exhaustion | medium | strong | strong | no | sometimes | for leaks |
| 9 Blocking work | medium | medium | strong | no | no | no |
| 10 No caching | weak | medium | medium | no | no | no |
| 11 Cold starts | weak | medium | strong | no | no | no |
| 12 No load shedding | weak | weak | strong | no | no | no |

Defects 1 to 4 can be judged from counts on a single machine, with no concurrent load. That makes them the place to start: deterministic findings that can run on the owner's laptop, inside ITTEN's rule about timing runs, and in the loop of a coding agent that writes the service. Defects 6 to 9 and 12 need concurrency or a misbehaving dependency, so their load checks run in CI.
